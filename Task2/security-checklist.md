# Задание 2. Проверочный лист безопасности бизнес-систем PropDevelopment

## 1. Идентификация систем и их характер с точки зрения безопасности

| Система | Домен | Ключевые данные | Внешние пользователи | Интеграции | Особенности с точки зрения ИБ |
| --- | --- | --- | --- | --- | --- |
| **Витрина продаж** (React) | Продажи | Публичный каталог, сессии клиентов | Клиенты (через firewall) | REST → backend-сервисы | Точка входа для потенциальных покупателей; передаёт контактные данные при бронировании |
| **client-mart-estate-app** + PostgreSQL | Продажи | Данные об объектах недвижимости | Нет (только API) | REST, gRPC ← госорганы | Хранит реестр объектов; интеграция с государственными регистрационными органами |
| **client-mart-app** + PostgreSQL | Продажи | ПДн клиентов, данные онлайн-сделок | Клиенты (через витрину) | REST, gRPC ↔ client-tour-app, госорганы | Критичная система: юридически значимые сделки; несколько точек регистрации клиента |
| **client-tour-app** + PostgreSQL | Продажи | ПДн, результаты осмотров/туров | Клиенты | gRPC ↔ client-mart-app | Связана с бронированием; фиксирует результаты осмотра, привязанные к клиенту |
| **client-crm-app** (Dynamics CRM) + MSSQL | Продажи | ПДн клиентов, история взаимодействий | Менеджеры (внутренние) | REST, JDBC | Отдельная БД и модель данных; одна из точек регистрации клиента без координации с другими |
| **auth-service-1** + auth-db-1 | Продажи | Учётные данные, сессии клиентов | Клиенты | REST | Единый сервис аутентификации для группы сервисов продаж; хранит секретные данные |
| **Витрина сервисов для собственников** (mobile) | ЖКУ | Сессии собственников | Собственники (через firewall) | REST → tenant-core-app, CRM | Мобильный клиент; доступ к оплате ЖКУ, умному дому, данным УК |
| **tenant-core-app** + PostgreSQL | ЖКУ | ПДн собственников, данные услуг | Нет (только API) | gRPC ↔ CRM, REST → партнёры УК | Ядро сервисов для собственников; интеграция с API управляющих компаний |
| **CRM (ЖКУ)** + PostgreSQL | ЖКU | ПДн собственников | Менеджеры (внутренние) | gRPC ↔ tenant-core-app, REST → партнёры, платёжная система | **Наиболее уязвимая зона:** API партнёров без единых политик; возможен доступ к чужим данным УК |
| **accountant-service-1** + БД | Финансы | Финансовая отчётность, бухгалтерские записи | Бухгалтеры (внутренние) | JDBC | Секретные финансовые данные; доступ через Active Directory |
| **Active Directory** | Финансы / общее | Учётные записи сотрудников | Менеджеры, аналитики, бухгалтеры | — | Централизованная аутентификация внутренних пользователей |
| **Хранилище данных** (ClickHouse) + S3 | Дата | Агрегированные данные всех доменов | BI-аналитики (внутренние) | gRPC, JDBC, Kafka ← все домены | **Критичная зона:** нет ограничений на доступ к данным; блокирует развитие ML/AI |
| **Партнёрские API УК** (внешние) | Внешние | ПДн собственников, данные ЖК | Партнёры (УК) | REST | Контракты содержат избыточные ПДн; нет единого контроля доступа между УК |
| **Платёжная система**, **госорганы** | Внешние | Платёжные и юридические данные | — | REST / gRPC | Внешние интеграции с повышенными требованиями к защите канала и данных |

**Выявленные уязвимые паттерны:**
- Разрозненная аутентификация: auth-service-1 (клиенты/собственники) и Active Directory (сотрудники) не связаны единым реестром.
- Отсутствие централизованного авторизационного контроля между доменами «Продажи» и «ЖКУ».
- Множественные точки регистрации клиента (витрина → client-mart-app, client-crm-app, client-tour-app) без координации.
- API партнёров УК работают без единых политик безопасности.
- DWH (ClickHouse/S3) принимает данные без ограничений доступа на уровне классификации.

## 2. Выбор разделов проверочного листа

В шаблоне шести уроков первой темы представлены пять разделов (I–V). Ниже — обоснование включения или исключения каждого раздела с учётом проблем и приоритетов PropDevelopment.

### Включённые разделы

| Раздел | Включён | Обоснование |
| --- | --- | --- |
| **I. Управление доступом** | ✅ Да | **Приоритет № 1.** Прямо связан с двумя ключевыми проблемами компании: (1) клиенты видят чужие данные в личном кабинете — сбой авторизации/разграничения доступа; (2) партнёры УК получают доступ к данным чужих управляющих компаний — нарушение принципа минимальных привилегий. В ландшафте три независимых контура аутентификации (auth-service-1, AD, CRM Dynamics), нет единого реестра учётных записей. |
| **II. Безопасность данных** | ✅ Да | **Приоритет № 1.** Это заявленная «ключевая проблема и самое уязвимое место» компании. Нарушен контроль данных: несколько точек регистрации клиента, нет Data Governance, DWH не ограничивает доступ по классификации. Блокирует развитие BI/ML/AI и создаёт риски по 152-ФЗ. Раздел напрямую проверяет классификацию, шифрование, резервное копирование и управление жизненным циклом данных. |
| **III. Защита инфраструктуры** | ✅ Да | **Приоритет № 2.** Гибридная инфраструктура (собственный ЦОД + приватное облако + арендованные мощности) увеличивает поверхность атаки. Firewall используется только для внешних клиентов и собственников; внутренние потоки (gRPC между сервисами, Kafka → DWH) не описаны как сегментированные. Партнёрские интеграции выходят за периметр firewall. Необходимо проверить сегментацию, мониторинг и контроль периметра. |
| **IV. Управление инцидентами** | ✅ Да | **Приоритет № 2.** Компания уже столкнулась с инцидентами (отображение чужих ФИО), обеспокоена утечкой у конкурента и готовится к комплексному аудиту. При этом один специалист по ИБ и нарушена передача информации между командами — высокий риск запоздалого обнаружения и некоординированного реагирования. |
| **V.1. Общие вопросы (специфические)** | ✅ Да | **Приоритет № 3.** Мобильное приложение для собственников — один из ключевых продуктов компании; вопросы MDM, удалённого доступа и облачного резервного копирования актуальны для гибридной инфраструктуры и S3-хранилища DWH. |

### Исключённый раздел

| Раздел | Включён | Обоснование |
| --- | --- | --- |
| **V.2. Управление оборудованием и физическая безопасность** | ❌ Нет | В описании системы и на диаграмме C4 отсутствуют данные о физической защите серверных помещений, СКУД и инвентаризации оборудования. Аудит сфокусирован на **бизнес-системах** и потоках данных, а не на физической инфраструктуре ЦОД. Раздел не связан напрямую с зафиксированными инцидентами (утечка ПДн через приложения и API). При наличии данных о собственном ЦОД раздел может быть добавлен на следующей итерации аудита. |

## 3. Проверочный лист безопасности бизнес-систем

| № | Вопрос | Да/нет | Комментарий |
| --- | --- | --- | --- |
| **I. Управление доступом** | | | |
| 1 | Используется ли многофакторная аутентификация (MFA) для доступа к критическим системам и сервисам? | **Нет** | MFA не описана ни для auth-service-1 (клиенты/собственники), ни для Active Directory (сотрудники). Критичные системы — client-mart-app (онлайн-сделки), CRM ЖКУ, accountant-service-1 — не защищены вторым фактором. |
| 2 | Настроены ли требования к сложности паролей и их регулярное обновление? | **Нет** | В описании архитектуры политика паролей не зафиксирована. auth-service-1 и AD используются без документированных требований к сложности и ротации. |
| 3 | Проводится ли аудит и пересмотр учётных записей с повышенными привилегиями на регулярной основе? | **Нет** | Один специалист по ИБ на всю компанию; после смены руководителей IT-комmand нарушена передача информации. Регулярный пересмотр привилегированных учётных записей не организован. |
| 4 | Реализован ли принцип минимальных привилегий при назначении ролей и прав доступа? | **Нет** | Зафиксированы случаи, когда партнёр одной УК через API видит и изменяет данные клиентов и ЖК, относящихся к другой компании. Клиенты видят чужие ФИО в личном кабинете — нарушение изоляции данных на уровне приложения. |
| 5 | Автоматически ли удаляются или деактивируются учётные записи после увольнения или изменения должности сотрудников? | **Нет** | Процесс деактивации учётных записей в AD и смежных системах не описан. При текущих проблемах с координацией между командами высок риск «зависших» учётных записей. |
| 6 | Ведётся ли журналирование всех операций доступа к системам и данным? Кто имеет доступ к журналам? | **Частично** | Логи интеграций ведутся без ПДн, но централизованного журналирования доступа к клиентским и собственническим данным нет. Инцидент с чужими ФИО обнаружен по жалобам клиентов, а не через журналы. |
| 7 | Используются ли механизмы контроля доступа на основе атрибутов для повышения гибкости управления доступом? | **Нет** | Разграничение доступа обусловлено бизнес-процессами между продуктами, а не атрибутной моделью (ABAC). Партнёрские API не используют атрибуты (УК, ЖК, собственник) для фильтрации данных. |
| 8 | Используются ли системы аутентификации пользователей для доступа к системам? | **Да** | auth-service-1 + auth-db-1 обеспечивают аутентификацию клиентов и собственников. Active Directory — аутентификацию внутренних сотрудников (менеджеры, аналитики, бухгалтеры). |
| 9 | Созданы ли замкнутые контуры для подсистем, работающих с чувствительными данными? | **Нет** | Данные из client-crm-app, client-mart-app, tenant-core-app и CRM ЖКУ поступают в DWH без ограничений. Партнёрские API УК не изолированы в отдельные контуры по управляющим компаниям. |
| 10 | Ограничен ли доступ к системам из внешних источников? | **Частично** | Firewall защищает доступ клиентов и собственников к витринам. Однако API партнёров УК и интеграции с госорганами и платёжной системой выходят за периметр firewall без описанных единых политик. |
| 11 | Ведётся ли единый реестр учётных записей? | **Нет** | Клиент может быть зарегистрирован в client-mart-app (бронирование), client-crm-app и client-tour-app независимо. У собственников — отдельный контур в CRM ЖКУ. Единого реестра нет. |
| 12 | Используются ли средства управления учётными записями на базе единого реестра? | **Нет** | Отсутствие единого реестра делает невозможным централизованное IDM. auth-service-1 и AD работают изолированно друг от друга. |
| 13 | Применяются ли средства для отзыва прав доступа? | **Нет** | Нет описания процессов отзыва прав при смене статуса клиента (покупатель → собственник) или при прекращении партнёрства с УК. API-ключи партнёров не управляются централизованно. |
| 14 | Используются ли средства централизованного контроля доступа? | **Нет** | Каждый домен (Продажи, ЖКУ, Финансы) реализует собственный контроль доступа. gRPC/REST-взаимодействия между сервисами не проходят через единый API Gateway с политиками безопасности. |
| **II. Безопасность данных** | | | |
| 1 | Разработана ли политика классификации данных, и актуализируется ли она в соответствии с действующим законодательством? | **Нет** | Формальная политика классификации отсутствует (проводится в рамках текущего аудита). Требования 152-ФЗ не верифицированы для всех бизнес-процессов. Классификация по ISO 27001 выполняется впервые. |
| 2 | Используется ли шифрование на уровне базы данных, файловой системы и при передаче данных по сети? | **Частично** | REST/gRPC используются для передачи данных; HTTPS для внешних витрин предполагается (firewall). Шифрование PostgreSQL, MSSQL, ClickHouse и S3 на уровне хранения не подтверждено описанием архитектуры. |
| 3 | Реализованы ли механизмы управления ключами шифрования? | **Нет** | Управление ключами не описано. auth-db-1 хранит учётные данные; API-ключи партнёров УК управляются командами разработки без единого KMS. |
| 4 | Проводится ли регулярное резервное копирование данных? Хранятся ли резервные копии в защищённых хранилищах? | **Да** | Для всех баз данных выполняется резервное копирование на глубину, необходимую для восстановления. Уровень защиты хранилищ резервных копий не детализирован. |
| 5 | Выполняется ли регулярное тестирование процесса восстановления данных из резервных копий? | **Нет** | Процедуры тестового восстановления не описаны. При гибридной инфраструктуре (ЦОД + облако) это создаёт риск неработоспособности backup при аварии. |
| 6 | Ограничен ли доступ к резервным копиям данных, и зашифрованы ли они? | **Нет** | Доступ к резервным копиям и их шифрование не описаны. Резервные копии содержат ПДн клиентов и собственников — требуют такой же защиты, как первичные данные. |
| 7 | Ведётся ли учёт персональных данных, и применяются ли специальные процедуры обработки и хранения для различных типов данных? | **Нет** | ПДн обрабатываются в client-crm-app, client-mart-app, tenant-core-app, CRM ЖКУ и передаются партнёрам без единых процедур. Несколько точек регистрации клиента без координации. |
| 8 | Осуществляется ли мониторинг доступа к данным на основе их классификации? Используются ли метки безопасности для маркировки данных? | **Нет** | **Ключевая проблема:** со стороны DWH (ClickHouse/S3) нет ограничений на доступ к данным. Метки безопасности и мониторинг по классификации не реализованы. |
| 9 | Разработаны ли процессы и системы Data Governance для управления данными? | **Нет** | **Ключевая проблема:** внутренние потоки данных между IT-продуктами не контролируются системно. Data Governance отсутствует, что блокирует развитие BI/ML/AI-продуктов. |
| 10 | Реализованы ли системы или процессы безопасного уничтожения данных? | **Нет** | Процедуры удаления ПДн при отзыве согласия или завершении договора не описаны. При дублировании данных в нескольких БД риск несогласованного хранения высок. |
| 11 | Используются ли системы или процессы контроля целостности данных? | **Нет** | Искажение/подмена данных клиента (чужие ФИО в ЛК) указывает на отсутствие контроля целостности и согласованности между системами. |
| 12 | Реализованы ли системы или процессы контроля сохранности данных? | **Частично** | Резервное копирование реализовано (п. II.4). Однако контроль сохранности при передаче между доменами (gRPC client-mart-app ↔ client-tour-app, Kafka → DWH) не описан. |
| 13 | Применяются ли средства или процессы анонимизации данных? | **Нет** | BI-аналитики работают с DWH напрямую. Анонимизация/псевдонимизация для аналитики и ML не применяется, хотя компания планирует AI-сервисы. |
| 14 | Разработана ли инструкция по процессу восстановления данных? | **Нет** | Формальная инструкция по восстановлению не описана, несмотря на наличие резервного копирования. |
| **III. Защита инфраструктуры** | | | |
| 1 | Используется ли межсетевой экран для ограничения входящего и исходящего трафика? | **Да** | Firewall размещён между внешними пользователями (клиенты, собственники) и витринами продаж и сервисов. Это подтверждено диаграммой C4. |
| 2 | Реализована ли сегментация сети на логические зоны (DMZ, корпоративная сеть, гостевая сеть) для ограничения доступа к критическим ресурсам? | **Частично** | Firewall выделяет внешний периметр. Сегментация между внутренними сервисами (продажи ↔ ЖКУ ↔ DWH), DMZ и корпоративной сетью не описана. Гибридная инфраструктура усложняет сегментацию. |
| 3 | Используются ли IDS/IPS-системы для обнаружения и предотвращения сетевых атак? | **Нет** | IDS/IPS не упомянуты в описании инфраструктуры. |
| 4 | Настроен ли мониторинг сетевого трафика на предмет аномалий и возможных атак, например, DDoS? | **Нет** | Мониторинг сетевого трафика не описан. Витрины продаж и мобильное приложение — публичные точки входа, уязвимые к DDoS. |
| 5 | Проводится ли регулярное сканирование уязвимостей операционных систем, приложений и сетевых устройств? | **Нет** | Компания только готовится к комплексному аудиту безопасности. Регулярное сканирование уязвимостей не организовано. |
| 6 | Установлены ли на серверах и рабочих станциях антивирусные программы и системы EDR? | **Нет** | Данных о AV/EDR в описании архитектуры нет. |
| 7 | Отключены ли неиспользуемые службы и порты на серверах, рабочих станциях и сетевом оборудовании? | **Нет** | Нет данных для оценки. Множество открытых REST/gRPC-интерфейсов между сервисами повышает поверхность атаки. |
| 8 | Используются ли механизмы контроля целостности системных файлов? Ведётся ли журналирование доступа к системным ресурсам? | **Частично** | Журналирование на уровне приложений ограничено (логи интеграций без ПДн). Контроль целостности системных файлов на серверах не описан. |
