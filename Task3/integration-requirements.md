# Задание 3. Требования к внешним интеграциям — сервисы «Умный дом»

## 1. Обзор интеграции

PropDevelopment подключает партнёрскую платформу «Умный дом» для двух сервисов:

| Сервис | Функции | Чувствительные данные |
| --- | --- | --- |
| **Интеллектуальный домофон** | Видеовызов, открытие по звонку, распознавание лица, автоматическое открытие | Биометрия (лицо), видеопоток, журнал доступа |
| **Интеллектуальный шлагбаум** | Удалённое открытие, распознавание номеров, автоматический въезд | Госномера ТС, журнал въезда/выезда |

**Принцип интеграции:** мобильное приложение собственника взаимодействует только с `smart-home-app` внутри PropDevelopment. Прямой доступ мобильного клиента к API партнёра **запрещён** — это устраняет проблемы некontролируемых партнёрских API, выявленные в Task 2.

```
Собственник → [Mobile App] → [smart-home-app] → [Платформа партнёра] → Устройства
                                    ↕
                          tenant-core-app / CRM / auth-service
```

## 2. Требования к безопасности

### 2.1. Общие требования

| ID | Требование | Обоснование |
| --- | --- | --- |
| SEC-01 | Все каналы связи — только **TLS 1.2+** (внешние) и **mTLS** (межсервисные backend-to-backend) | Защита ПДн и биометрии при передаче |
| SEC-02 | Биометрические шаблоны и фото лиц **не хранятся** в PropDevelopment; обработка — только на стороне партнёра | Соответствие 152-ФЗ (биометрические ПДн — отдельный правовой режим) |
| SEC-03 | Госномера и видеокадры хранятся в PropDevelopment **не более 72 часов** (буфер событий); долговременное хранение — только обезличенные метаданные | Минимизация данных (data minimization) |
| SEC-04 | Каждый запрос к партнёру содержит **идентификатор ЖК (`residential_complex_id`)**; партнёр обязан фильтровать данные строго в рамках этого tenant | Устранение проблемы доступа партнёра одной УК к данным другой |
| SEC-05 | Все операции управления доступом (открытие двери, шлагбаума) **журналируются** в `smart-home-db` с привязкой к `owner_id`, `device_id`, timestamp, результат | Аудит и расследование инцидентов |
| SEC-06 | Партнёр обязан поддерживать **rate limiting** и защиту от brute-force на API управления устройствами | Предотвращение несанкционированного физического доступа |
| SEC-07 | Webhook-события от партнёра принимаются **только с верифицированной подписью HMAC-SHA256** и IP-allowlist | Защита от подмены событий |
| SEC-08 | Видеопоток домофона передаётся через **краткоживущий signed URL / WebRTC token** (TTL ≤ 5 мин), выдаваемый `smart-home-app` | Исключение постоянных открытых потоков |
| SEC-09 | Доступ собственника к устройствам другого ЖК/квартиры **технически невозможен** — проверка через `tenant-core-app` + CRM перед каждой командой | Устранение инцидентов «чужих данных в ЛК» |
| SEC-10 | API-ключи партнёра хранятся в **KMS/Vault**, ротация — не реже 1 раза в 90 дней | Секретные данные (Task 1) |
| SEC-11 | Передача данных в DWH — только **обезличенные события** (timestamp, device_type, event_type, result); без ПДн и биометрии | Data Governance, развитие BI/ML |
| SEC-12 | Партнёр обязан предоставить **DPA (соглашение об обработке ПДн)** и подтверждение соответствия 152-ФЗ | Законодательные требования компании |

### 2.2. Требования по сервисам

**Интеллектуальный домофон:**

| ID | Требование |
| --- | --- |
| SEC-I01 | Регистрация лица в системе — только с **явного согласия** собственника в мобильном приложении |
| SEC-I02 | Список лиц с доступом привязан к **конкретной квартире/подъезду**, не ко всему ЖК |
| SEC-I03 | Удалённое открытие двери — только для **аутентифицированного собственника** с MFA (рекомендуется) |
| SEC-I04 | Видеовызов инициирует push-уведомление; содержимое видео **не кэшируется** на устройстве партнёра дольше сессии |

**Интеллектуальный шлагбаум:**

| ID | Требование |
| --- | --- |
| SEC-B01 | Белый список номеров привязан к **owner_id + parking_slot**; один номер — один собственник |
| SEC-B02 | Автоматическое распознавание номера не даёт доступ, если номер **не в whitelist** текущего ЖК |
| SEC-B03 | Ручное открытие шлагбаума из приложения — с **подтверждением** (push + PIN/biometric device) |

## 3. Протоколы аутентификации и авторизации

### 3.1. Схема аутентификации

| Участник | Протокол | Механизм | Назначение |
| --- | --- | --- | --- |
| **Собственник → Mobile App** | OAuth 2.0 / OIDC | Authorization Code + PKCE через **Keycloak** (`auth-service-1`) | Аутентификация пользователя, выдача JWT access/refresh token |
| **Mobile App → smart-home-app** | HTTPS + Bearer JWT | JWT (RS256), scopes: `smart-home:read`, `smart-home:control`, `smart-home:video` | Авторизация запросов собственника; token introspection через Keycloak |
| **smart-home-app → tenant-core-app** | gRPC + mTLS | Service account JWT, внутренний CA | Проверка: собственник ↔ квартира ↔ ЖК |
| **smart-home-app → CRM (ЖКУ)** | gRPC + mTLS | Service account JWT | Получение привязки собственника к объекту недвижимости |
| **smart-home-app → Платформа партнёра** | OAuth 2.0 Client Credentials + mTLS | Client ID/Secret (Vault), mutual TLS client certificate | Machine-to-machine; один credential set **на каждый ЖК** |
| **Платформа партнёра → smart-home-app** (webhook) | HTTPS + HMAC | Shared secret per ЖК, заголовок `X-Signature: HMAC-SHA256(body, secret)` | Аутентификация входящих событий |
| **Mobile App ← видеопоток** | WebRTC / WSS | Short-lived token от smart-home-app (TTL 5 мин) | Безопасная передача видео без прямого доступа к партнёру |

### 3.2. Модель авторизации

- **RBAC** на уровне Keycloak: роль `owner` с scopes по умолчанию `smart-home:read`.
- **ABAC** на уровне `smart-home-app`: атрибуты `owner_id`, `apartment_id`, `residential_complex_id`, `device_id` — каждая команда проверяется по полному набору атрибутов.
- **Tenant isolation**: OAuth Client Credentials партнёра scoped to `residential_complex_id`; партнёр не может запросить данные другого ЖК.

### 3.3. JWT Claims (mobile → smart-home-app)

```json
{
  "sub": "owner-uuid",
  "scope": "smart-home:read smart-home:control",
  "residential_complex_id": "zhk-123",
  "apartment_id": "apt-456",
  "exp": 1719500000
}
```

## 4. Организация взаимодействия между системами

### 4.1. Компоненты и роли

| Компонент | Роль в интеграции |
| --- | --- |
| **Витрина сервисов для собственников** (Mobile App) | UI: управление домофоном/шлагбаумом, просмотр видео, управление whitelist |
| **auth-service-1** (Keycloak) | Аутентификация собственника, выдача и валидация JWT |
| **smart-home-app** | **Единая точка интеграции** с партнёром; оркестрация, авторизация, аудит |
| **smart-home-db** | ACL устройств, whitelist номеров/гостей, журнал событий |
| **tenant-core-app** | Верификация прав собственника на объект |
| **CRM (ЖКУ)** | Мастер-данные: собственник ↔ квартира ↔ ЖК |
| **Платформа «Умный дом»** (партнёр) | Управление физическими устройствами, биометрия, LPR |
| **Хранилище данных** (DWH) | Аналитика обезличенных событий доступа |

### 4.2. Потоки взаимодействия

**Поток 1 — Удалённое открытие домофона собственником:**

1. Собственник нажимает «Открыть» в Mobile App.
2. App отправляет `POST /api/v1/intercom/{deviceId}/open` + JWT → `smart-home-app`.
3. `smart-home-app` валидирует JWT через Keycloak.
4. `smart-home-app` → `tenant-core-app` [gRPC]: проверка `owner_id` ↔ `device_id` ↔ `apartment_id`.
5. `smart-home-app` → Партнёр [REST, mTLS]: `POST /devices/{id}/open` + OAuth token scoped to ЖК.
6. Партнёр выполняет команду, возвращает результат.
7. `smart-home-app` записывает событие в `smart-home-db`, возвращает статус в App.

**Поток 2 — Видеовызов домофона (входящий):**

1. Посетитель нажимает кнопку домофона → Партнёр генерирует событие.
2. Партнёр → `smart-home-app` [Webhook, HMAC]: `{event: "intercom_call", device_id, apartment_id}`.
3. `smart-home-app` определяет `owner_id`, отправляет push в Mobile App.
4. App запрашивает `GET /api/v1/intercom/{deviceId}/stream-token` → получает short-lived WebRTC token.
5. App устанавливает видеосессию через token (прокси/partner CDN); PropDevelopment не хранит видео.

**Поток 3 — Автоматическое открытие шлагбаума по номеру:**

1. Камера LPR на шлагбауме распознаёт номер → Партнёр сверяет с whitelist.
2. Партнёр → `smart-home-app` [Webhook]: `{event: "barrier_opened", plate_number, device_id, method: "auto"}`.
3. `smart-home-app` записывает событие, отправляет push собственнику (опционально).
4. Синхронизация whitelist: `smart-home-app` → Партнёр [REST]: `PUT /devices/{id}/plates` при изменении списка в App.

**Поток 4 — Регистрация биометрии лица:**

1. Собственник даёт согласие в App → `POST /api/v1/intercom/{deviceId}/faces` + фото.
2. `smart-home-app` проверяет права, **не сохраняет фото**, проксирует → Партнёр [REST]: регистрация биометрического шаблона.
3. Партнёр хранит шаблон; PropDevelopment хранит только `face_ref_id` + metadata в `smart-home-db`.

### 4.3. API-контракт (smart-home-app ↔ Партнёр)

| Метод | Endpoint (партнёр) | Назначение |
| --- | --- | --- |
| `POST` | `/v1/devices/{id}/open` | Открыть домофон / шлагбаум |
| `GET` | `/v1/devices/{id}/status` | Статус устройства |
| `PUT` | `/v1/devices/{id}/access-list/faces` | Синхронизация whitelist лиц |
| `PUT` | `/v1/devices/{id}/access-list/plates` | Синхронизация whitelist номеров |
| `POST` | `/v1/devices/{id}/faces` | Регистрация биометрии |
| `DELETE` | `/v1/devices/{id}/faces/{faceRefId}` | Удаление биометрии |
| `POST` | `/v1/stream/session` | Получение WebRTC/session token для видео |
| `POST` | `/v1/webhooks/subscribe` | Регистрация webhook URL PropDevelopment |

### 4.4. Нефункциональные требования к интеграции

| Параметр | Требование |
| --- | --- |
| Доступность API партнёра | SLA ≥ 99.5%; fallback: ручное открытие через классический домофон |
| Latency команды «открыть» | ≤ 2 сек (p95) end-to-end |
| Latency webhook | ≤ 500 мс от события до push собственнику |
| Идемпотентность | Все команды управления — с заголовком `Idempotency-Key` |
| Версионирование API | URI versioning (`/v1/`), backward compatibility ≥ 12 месяцев |
| Мониторинг | Метрики интеграции в SIEM; алерт при error rate > 1% |

## 5. Изменения в ландшафте (сводка)

| Изменение | Тип | Описание |
| --- | --- | --- |
| `smart-home-app` | **Новый контейнер** | Интеграционный сервис, единая точка выхода к партнёру |
| `smart-home-db` | **Новая БД** | ACL, whitelist, audit log |
| Платформа «Умный дом» | **Новая внешняя система** | Партнёрский SaaS |
| Mobile App | **Доработка** | UI домофона и шлагбаума |
| `tenant-core-app`, CRM | **Доработка API** | Endpoint проверки прав на устройства |
| auth-service-1 | **Доработка** | Новые scopes для smart-home |
| DWH | **Доработка pipeline** | Приём обезличенных событий из smart-home-db |
